The decision

One hard call created by the launch: budget alerts today fire after spend crosses a threshold. With team leads now added as Budget Viewers, should we also send a forecast alert, and how confident must the forecast be before it emails anyone?

customer problem

A platform lead sets a $9k monthly budget for a team's serverless jobs, SQL and pipelines. A runaway job on day 9 doubles daily spend. The threshold email lands on day 24, up to a day late, when the money is already gone. Finance asks, "why didn't anyone warn us?"

What admins want is a heads-up while there is still time to act: pause a schedule, right-size a warehouse, or raise the budget on purpose.

pinned to customer pain
proposed change

Add an opt-in "likely to exceed" alert to each budget. Every day, simulate the rest of the month from recent usage. If the odds of ending over the threshold reach C%, email once per month with the odds and the top drivers.

success metric

Early-warning rate: share of over-budget months where admins are warned at least 5 days before spend crosses the line. Target ≥ 60% (today ≈ 0%).

guardrails
  • False alarms ≤ 15% of on-budget months
  • Recall (any warning before the cross) ≥ 70%
  • Median lead time ≥ 5 days
  • ≤ 1 forecast email per budget per month
stakeholders

Account and workspace admins (budget owners), the new Budget Viewers (team leads), FinOps and finance, the billing platform engineers who own the usage tables, support (who field "surprise bill" tickets), and account executives.

The math, from my Monte Carlo course

inverse CDF, discrete

To draw "how many jobs run today", list the possible counts with their probabilities, stack the cumulative sums on [0,1], drop a uniform U, and take the first count whose cumulative sum passes U. Weekdays and weekends get different tables.

N = min{ n : F(n) ≥ U }, U ~ Unif(0,1)
inverse CDF, exponential

A single-stage run's cost is memoryless: most are cheap, a few are long. Invert the exponential CDF and you get it from one uniform. A runaway job's length uses the geometric version of the same trick.

X = −θ · ln(U) · L = ⌈ ln U / ln(1−p) ⌉
convolution

A real run has stages (spin-up, read, transform, write). Adding k independent exponential stages is a convolution, and the sum is Erlang(k, θ): same mean kθ, less spiky as k grows. That's the burstiness slider. Adding up runs, days and workloads is more convolution, and that sum is the month-end bill.

Run = Σi=1..k −θ ln Ui ~ Gamma(k, θ)
a shortcut for the backtest

Sums of Gammas with the same scale stay Gamma, so N runs of Erlang(k, θ) add up to Gamma(Nk, θ). With Nk in the hundreds, the CLT lets the backtest draw that total with a single Box-Muller normal, about 50× faster, so 160 months × 26 days × 150 futures runs in a blink.

Σ ≈ Nkθ + √(Nk)·θ·Z, Z = √(−2 ln U₁) cos(2πU₂)

How I'd run it on real data

Illustrative only. Serverless usage lives in system.billing.usage (filter product_features.is_serverless, split by billing_origin_product) joined to system.billing.list_prices. The table finops.sandbox.* is a made-up name.

-- 1. Daily run counts and per-run cost, last 90 days
CREATE OR REPLACE TABLE finops.sandbox.daily_runs AS
SELECT u.usage_date,
       u.billing_origin_product         AS workload,
       dayofweek(u.usage_date) IN (1,7)  AS is_weekend,
       count(DISTINCT coalesce(u.usage_metadata.job_run_id,
             u.usage_metadata.dlt_pipeline_id,
             u.usage_metadata.notebook_id)) AS runs,
       sum(u.usage_quantity * p.pricing.default) AS list_cost
FROM system.billing.usage u
JOIN system.billing.list_prices p
  ON u.sku_name = p.sku_name
 AND u.usage_start_time >= p.price_start_time
 AND (p.price_end_time IS NULL
      OR u.usage_start_time < p.price_end_time)
WHERE u.product_features.is_serverless
  AND u.usage_date >= date_sub(current_date(), 90)
GROUP BY ALL;

-- 2. Inverse-CDF tables: P(runs = n | workload, weekend)
SELECT workload, is_weekend, runs,
       count(*) / sum(count(*)) OVER
         (PARTITION BY workload, is_weekend) AS p
FROM finops.sandbox.daily_runs
GROUP BY ALL;
# 3. Simulate the rest of the month (PySpark + NumPy)
import numpy as np
rng = np.random.default_rng(111)

def forecast(spent, today, tables, theta, k, rate=1.0,
             days=30, sims=5000):
    total = np.full(sims, spent)
    for d in range(today + 1, days + 1):
        wknd = (d % 7) in (0, 6)
        for w, (vals, probs) in tables[wknd].items():
            n = rng.choice(vals, size=sims, p=probs)   # inverse CDF
            # Erlang(k) per run, n runs -> Gamma(n*k)
            total += rate * rng.gamma(n * k[w] + 1e-9, theta[w])
    return np.percentile(total, [30, 50, 90])

p30, p50, p90 = forecast(spent=4210.0, today=10, ...)
if p30 > budget  # odds of overspend >= 70%
   and not already_alerted_this_month:
    send_forecast_alert(budget_id, odds=(sim > budget).mean())
